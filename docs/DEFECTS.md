# Defect register

What the translation of EPA SWMM 5.2.4 into safe Rust found in the C. Generated by `app/build.py` from the same list the app's Inside tab shows; every code excerpt is taken from the v5.2.4 source at build time.

* **RS-1 to RS-4** are reproduced on purpose: the output must match EPA byte for byte, defects included.
* **RS-5 to RS-10** are undefined behaviour in C (out-of-bounds or NULL accesses). EPA's output there depends on memory and on the platform, so there is nothing to reproduce; swmm5-rust stops with a message naming the line, or, for RS-9, writes the error report, or, for RS-10, reads 0.0 where C reads far outside a table. The gate counts these decks apart.

Other places where C's behaviour is undefined, and what the Rust does there, are listed in [UNDEFINED.md](UNDEFINED.md).

## RS-1: storage_getVolDiff() passes a storage index where a node index belongs

*Status: reproduced. Where: node.c, lines 923-925.*

For FUNCTIONAL (with a Newton solve), CONICAL and PYRAMIDAL storage under kinematic-wave or steady routing, the depth found for a given volume uses the storage curve of whatever unit node k points at. Same network in two section orders: peak depth in S2 is 9.82 ft with the outfall listed before the storage units and 10.43 ft with the storage units first. Try it on this tab.

Reported earlier as NUM-55 in the OpenSWMM 2026 code review, which also found the second fault on the same lines: in metric models the solve mixes user units and feet, and depths come out about ten times too small. Fixed in the OpenSWMM fork (commit 3d09a10a); EPA 5.2.4 has it. The review's decks NUM-55_cms and NUM-55_cfs-junction-first are in the gate and match EPA.

```c

    // --- compute volume & surface area at depth y
    *f = storage_getVolume(k, y) - storageVol->v;
    *df = storage_getSurfArea(k, y);
```

## RS-2: LID parameter errors print the message template instead of the LID name

*Status: reproduced. Where: report.c line 1433; lid.c lines 984, 999, 1011, 1028, 1041, 1155, 1170 and 1177.*

lid.c builds "<LID name> <layer>" in the global Msg and passes Msg; report_writeErrorMsg() then reuses Msg for the template. The deck tests/models/lid_error_message.inp gets `ERROR 185: invalid parameter value for LID` followed by the template again, ending `%s..`, in all three engines.

Not among the OpenSWMM 2026 code review's entries; we found no earlier report of it.

```c
        WRITE("");
        fprintf(Frpt.file, error_getMsg(code, Msg), s);
```

## RS-3: FILLED_CIRCULAR geometry edits the link's full depth and area as it reads them

*Status: reproduced. Where: xsect.c, filled_circ_* functions.*

The add-then-subtract round trip can leave yFull or aFull one bit lower, and C keeps the change in Link[j].xsect. A first Rust translation that worked on copies differed from EPA in 13 of 7,848 .out values (largest 3.8e-06) and in one time of maximum depth, 01:04 against EPA's 01:06. Fixed by writing the copy back. The independent review found one more read that used a copy, the link velocity a control rule asks for; it now goes through the same path (tests/models/filled_circ_control.inp).

Not among the OpenSWMM 2026 code review's entries; we found no earlier report of it. It is harmless to the physics (one bit), but it is state that C changes as a side effect of reading.

```c
    double y;

    // --- temporarily remove filled portion of circle
    xsect->yFull += xsect->yBot;
    xsect->aFull += xsect->aBot;
    a += xsect->aBot;

    // --- find depth in unfilled circle
    y = circ_getYofA(xsect, a);

    // --- restore original values
    y -= xsect->yBot;
    xsect->yFull -= xsect->yBot;
    xsect->aFull -= xsect->aBot;
    return y;
}
```

## RS-4: Out-of-range float-to-int conversions are undefined in C

*Status: x86 behaviour reproduced. Where: gage.c line 251 (and 61 other conversions).*

gage.c line 251 converts about 8.6e14 to int for any one-point rain series. x86 gives -2,147,483,648, Rust's `as` gives +2,147,483,647, and the difference decides whether WARNING 09 is written. It changed 12 reports in the c2rust translation until every conversion went through ccast.

Reported as CRASH-21 in the OpenSWMM 2026 code review, and met earlier by Bob Dickinson's c2rust port, swmm5-rs, where it was the cause of 25 reports differing from EPA's by one WARNING 09 line.

```c
        gageInterval = (int)(floor(Tseries[k].dxMin*SECperDAY + 0.5));
        if ( gageInterval > 0 && Gage[j].rainInterval > gageInterval )
        {
            report_writeErrorMsg(ERR_RAIN_GAGE_INTERVAL, Gage[j].ID);
        } 
```

## RS-8: CRASH-04: a quoted "Shape" leaves the Shape array empty, and project_validate() writes into it

*Status: Rust stops; C aborts. Where: project.c line 227.*

The counting pass compares the token with its quotes; the reading pass strips them. Native EPA aborts on heap corruption; the WebAssembly build traps in node, and in the headless Chromium used to test this page the same access crashed the whole renderer, so the page runs this deck only in swmm5-rust. swmm5-rust stops at the index.

CRASH-04 in the OpenSWMM 2026 code review.

```c
    {

            Curve[i].refersTo = j;
            Shape[j].curve = i;
```

## RS-9: CRASH-08: controls_delete() walks a NULL Expression array after an early input error

*Status: Rust reports the error. Where: controls.c line 313.*

Native EPA segfaults on close and leaves a 0-byte report. In WebAssembly EPA survives and writes the ERROR 205/207 report, byte-identical to swmm5-rust's. The Rust loop finds an empty Vec and touches nothing.

## RS-10: CRASH-07: a NaN or overflowing ratio indexes a cross-section table far outside its bounds

*Status: Rust reads 0.0; C crashes natively. Where: xsect.c line 1488 (and 1441, 1651).*

lookup() converts x/delta to an int with no check; a NaN or a huge ratio gives INT_MIN, and C reads 16 GB below the table. Native EPA segfaults. In WebAssembly the read lands in the module's own memory and EPA runs on. This is the one place the translators chose a value instead of stopping: an out-of-range read gives 0.0, because for a NaN ratio the result is NaN whatever is read. On CRASH-07_tiny-diameter all three WebAssembly engines then agree byte for byte; on CRASH-07_nan-diameter EPA's WebAssembly build reads something else and differs. The register says so rather than claim a match.

CRASH-07 in the OpenSWMM 2026 code review.

```c
    // --- find which segment of table contains x
    delta = 1.0 / ((double)nItems-1);
    i = (int)(x / delta);
    if ( i >= nItems - 1 ) return table[nItems-1];

    // --- compute x at start and end of segment
    x0 = i * delta;
```
